# 雏雁计划双端系统代码与技术实现方案

项目：面向老龄人群的网页无障碍体验提升技术研究与实现  
周期：2026 年 10 月至 2027 年 4 月  
负责人：苏越；组员：巩品言

## 1. 本期产品与验收边界

本期只对团队自建的演示网站完成三个任务：信息查询、预约表单、弹窗确认。若取得网站方许可，可用同一任务格式接入一个合作页面。本期不承诺自动操作任意网站，也不建设电脑系统级助手或实体键盘。

**开发者系统**用于发现和修复障碍：选择任务 → 运行浏览器评测 → 查看焦点轨迹、规则结果和截图 → 阅读 AI 解释与建议 → 人工改代码 → 用同一任务复测。第一版只需展示一个可复现、可修复的问题，例如表单字段缺少标签。

**用户系统**用于完成任务：从左侧快捷栏选择任务，或在聊天框描述目标 → 系统识别预设任务 → 分步展示进度和大字表单卡片 → 遇到不确定信息暂停提问 → 最终提交前展示核对卡片 → 用户确认后执行。第一版只需跑通演示网站的一次预约流程。

**最小验收**：三个任务脚本、一个开发端修复闭环、一个用户端 AI 辅助闭环、改进前后任务记录、安装与使用说明。

## 2. 技术选型与代码组织

采用一个 TypeScript 仓库，避免两人分别维护不兼容的前后端语言：

| 部分 | 建议实现 | 为什么现在选它 |
|---|---|---|
| 两套前端 | React + Vite + TypeScript | 共用任务类型、按钮与表单组件 |
| 服务端 | Fastify + TypeScript | 提供任务、评测、问题单和 AI 适配接口 |
| 浏览器评测 | Playwright + `@axe-core/playwright` | 可复现任务步骤并检查部分规则 |
| 数据存储 | SQLite；以 Prisma 管理表结构 | 本期单机演示即可，不需运维数据库服务器 |
| 模型接入 | 服务端统一 `ModelProvider` 接口 | 模型不可用时仍能运行固定任务流程 |

建议目录：

```text
apps/
  developer/       # 开发者工作台：导航、预览、问题、复测
  assistant/       # 用户端：快捷栏、聊天、进度、确认
  api/             # Fastify 路由、任务服务、模型适配
packages/
  contracts/       # 两端共用的 TaskSpec、Issue、RunRecord 类型
  evaluator/       # Playwright 执行、axe 检查、焦点与截图记录
  task-catalog/    # 人工审核过的任务定义
prisma/
  schema.prisma
tests/
  tasks/           # 三类端到端任务与回归测试
```

先用本机启动三个服务和演示网站。浏览器执行队列一次只跑一个任务，单次运行设超时；任务失败后关闭浏览器上下文并保留错误记录。稳定后再考虑把浏览器执行独立为进程。

两端共用同一个 API，但任务运行要区分用途。开发端创建独立的评测浏览器会话，用演示数据自动走完流程；用户端每次任务也创建独立会话，在需要补充资料或最终提交时暂停，把语义化表单卡片发回聊天界面。用户输入由服务端校验后继续运行，浏览器会话在完成、取消或超时后立即释放。开发端的“页面预览”显示演示站页面和证据截图；用户端以聊天状态与大字卡片呈现操作进度，不要求老年用户阅读自动化浏览器画面。

## 3. 两端共享的任务定义

任务步骤由团队编写并审查。模型只选择任务和填写经过校验的参数，不能返回任意 URL、CSS 选择器或脚本。定位控件优先使用可访问名称和角色，这也能暴露标签缺失等障碍。

```ts
// packages/contracts/task.ts
export type Step =
  | { kind: "click"; role: "link" | "button"; name: string }
  | { kind: "fill"; label: string; slot: "date" | "service" }
  | { kind: "expectText"; text: string }
  | { kind: "confirmSubmit"; buttonName: string };

export type TaskSpec = {
  id: "search" | "appointment" | "dialog";
  title: string;
  startPath: string;          // 只能是演示站内的相对路径
  successText: string;
  steps: Step[];
};
```

任务定义保存在代码仓库并随版本发布。服务端启动时校验 `startPath` 必须以单个 `/` 开头、不能以 `//` 开头，不接受绝对网址或脚本。部署配置另设允许的演示站域名；即使模型返回一个看似合法的网址，也不把它传给浏览器。

预约任务的首版步骤可写为：打开 `/appointment` → 找到“预约服务”入口 → 按标签填写服务与日期 → 打开核对信息 → 等待用户确认 → 点击“确认预约” → 检查成功提示。每一步都写明超时、失败原因和截图时机。

## 4. 开发者系统的可执行流程

### 4.1 评测记录

前端点击“运行评测”后，服务端创建 `RunRecord`，校验目标网址属于允许的演示站域名，然后启动一个新的 Playwright 浏览器上下文。每次运行至少记录：

- 任务编号、演示站版本、开始与结束时间、成功或失败；
- 每一步的控件名称、操作结果、耗时；
- 焦点变化序列及失败步骤截图；
- axe-core 规则命中，包括规则 ID、涉及控件和说明；
- 人工走查结果，例如屏幕阅读器是否读出字段名。

关键实现示例：

```ts
import { chromium } from "playwright";
import AxeBuilder from "@axe-core/playwright";

export async function evaluateTask(baseUrl: string, task: TaskSpec) {
  if (!task.startPath.startsWith("/") || task.startPath.startsWith("//")) {
    throw new Error("任务起点必须是站内路径");
  }
  const browser = await chromium.launch();
  const context = await browser.newContext();
  const page = await context.newPage();
  const focus: string[] = [];
  try {
    await page.exposeFunction("recordFocus", (name: string) => focus.push(name));
    await page.addInitScript(() => {
      document.addEventListener("focusin", (event) => {
        const el = event.target as HTMLElement;
        const name = el.getAttribute("aria-label")
          ?? el.getAttribute("name")
          ?? el.textContent?.trim().slice(0, 40)
          ?? el.tagName;
        (window as any).recordFocus(name);
      });
    });
    await page.goto(new URL(task.startPath, baseUrl).toString());
    const scan = await new AxeBuilder({ page }).analyze();
    // executeReviewedSteps 只执行 TaskSpec 中的 click/fill/expectText；
    // confirmSubmit 在用户端必须等待确认，评测端使用演示数据。
    const outcome = await executeReviewedSteps(page, task.steps);
    return { outcome, focus, violations: scan.violations };
  } finally {
    await context.close();
    await browser.close();
  }
}
```

`executeReviewedSteps` 按以下方式解释经过审核的任务步骤。运行前将 `slot` 的值从校验后的演示数据或用户表单中取得；每一步前检查匹配数，超时或不唯一时记为失败并截图。任务若导航到新页面或弹出新状态，再运行一次 axe 检查并标注对应步骤，避免只检查起始页面。`confirmSubmit` 是停点，不得像普通 `click` 一样自动越过。

```ts
import type { Page } from "playwright";

class MissingTaskValue extends Error {
  constructor(public slot: "date" | "service") {
    super(`缺少任务参数：${slot}`);
  }
}

async function runStep(page: Page, step: Step, values: Record<string, string>) {
  switch (step.kind) {
    case "click": {
      const target = page.getByRole(step.role, { name: step.name, exact: true });
      if (await target.count() !== 1) throw new Error(`控件不唯一：${step.name}`);
      await target.click({ timeout: 5000 });
      break;
    }
    case "fill": {
      const target = page.getByLabel(step.label, { exact: true });
      if (await target.count() !== 1) throw new Error(`字段不唯一：${step.label}`);
      const value = values[step.slot];
      if (!value) throw new MissingTaskValue(step.slot);
      await target.fill(value, { timeout: 5000 });
      break;
    }
    case "expectText":
      await page.getByText(step.text, { exact: true })
        .waitFor({ state: "visible", timeout: 5000 });
      break;
    case "confirmSubmit":
      return { pause: true, buttonName: step.buttonName } as const;
  }
  return { pause: false } as const;
}
```

执行器捕获 `MissingTaskValue` 后将状态改为“等待补充信息”，把缺失字段名返回给用户端表单卡片。评测脚本在 `confirmSubmit` 停点使用预先准备的虚构数据，并由测试配置明确允许继续；用户端则必须等到该会话收到本人确认。开发者工作台将失败步骤、焦点轨迹和截图放在同一问题卡片中。

### 4.2 AI 解释与修复建议

模型输入只包含规则 ID、问题控件附近的演示代码片段、焦点记录和任务失败步骤。要求返回 `原因`、`建议修改`、`仍需人工核对` 三栏。生成内容显示“AI 建议”，不自动写入源文件。开发者修改演示站代码后，点“查看差异并复测”；报告对比前后两次运行的相同任务指标。

服务端把建议结果保存到 `review_notes`，其中记录模型版本、生成时间和开发者是否采纳。若模型给出的修改无法对应到证据，界面允许标记“建议不适用”；问题是否解决只看修复后任务和人工走查结果。

第一版建议仅覆盖三类可清楚演示的问题：表单标签、焦点顺序、提交状态播报。对于颜色对比度等规则可显示检测结果，但不让模型声称已经验证用户体验。

## 5. 用户系统的可执行流程

快捷工具栏直接绑定三个 `TaskSpec`。聊天输入先交给模型识别任务 ID 与必要参数；模型失败或接口不可用时，显示三个可点击任务，不阻断使用。模型返回值先做结构校验，服务端再按任务 ID 调用预设步骤。

```ts
import { z } from "zod";

const Intent = z.object({
  taskId: z.enum(["search", "appointment", "dialog"]),
  service: z.string().max(40).optional(),
  date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/).optional()
}).strict();

export function chooseTask(modelOutput: unknown) {
  const intent = Intent.parse(modelOutput);
  return { intent, task: taskCatalog[intent.taskId] };
}
```

服务端还要独立检查日期是否有效、是否在演示站允许范围内。执行状态固定为 `待开始 → 执行中 → 等待补充信息 → 等待用户确认 → 正在提交 → 已完成/失败`。聊天气泡只负责说明状态；实际输入使用带标签的大字表单卡片。最终提交按钮只有在“等待用户确认”状态才可用，用户点击后才继续执行。

实现时用 `runId` 关联聊天会话、浏览器会话和当前步骤。`POST /assistant/intent` 只返回选中的任务和缺少的参数；`POST /runs` 创建会话并运行到下一个停点；`POST /assistant/runs/:id/confirm` 用数据库条件更新检查状态和确认令牌，只有成功把状态改为 `SUBMITTING` 的请求能执行提交。重复请求直接返回当前结果。若提交期间进程中断，显示“结果待核对”，不自动重试可能产生重复预约的动作。页面刷新后通过 `GET /runs/:id` 恢复进度。

```ts
// 服务端确认接口的核心约束：只有一次状态迁移能够成功
const changed = await db.run.updateMany({
  where: { id: runId, status: "WAITING_CONFIRMATION",
           confirmToken: body.confirmToken },
  data: { status: "SUBMITTING", confirmToken: null }
});
if (changed.count !== 1) return getRunResult(runId);
await submitReviewedButton(runId); // 只调用 TaskSpec 中审查过的确认按钮
```

用户端只在本期演示网站内完成任务。任务卡片可让用户检查日期和服务名称；如果页面的内容与任务定义不一致，执行器停止并报告失败，不让 AI 自行猜测下一步。

用户端最少实现：键盘可见焦点、语义化按钮和标签、状态更新的可读播报、可放大文字、返回与暂停。设计时用键盘和屏幕阅读器逐步走完整个预约流程。

## 6. 数据表与接口

建议数据表：

| 表 | 关键字段 | 用途 |
|---|---|---|
| `tasks` | `id, title, version, spec_json` | 保存经过审核的任务定义 |
| `runs` | `id, task_id, site_version, status, duration_ms, step_count` | 保存一次评测或用户任务 |
| `issues` | `id, run_id, step, rule_id, evidence_path, status` | 记录可复现的问题 |
| `review_notes` | `issue_id, suggestion, accepted, reviewer_note` | AI建议与人工决定 |
| `study_results` | `participant_code, task_id, version, success, duration_ms, steps, rating` | 试用对照指标 |

最少接口：`GET /tasks`、`POST /runs`、`GET /runs/:id`、`GET /runs/:id/issues`、`POST /issues/:id/review`、`POST /assistant/intent`、`POST /assistant/runs/:id/confirm`。所有会启动浏览器的接口只接受任务 ID，不接受任意网址；新网址由开发者配置并审核。

前端通过每秒查询一次 `GET /runs/:id` 获取简短状态即可，无需在首版引入实时推送。服务端只保存失败步骤的必要截图，文件名使用运行编号；定期清理演示截图，公开材料仅放虚构数据。对 API 增加任务超时、同一会话最多一次运行和错误日志，防止模型接口或浏览器异常导致任务一直占用资源。

建议保留三个固定演示验收脚本：① 标签缺失的预约字段在修复前被发现、修复后不再命中且键盘能完成；② 用户说“帮我预约周三的服务”后，模型选择预约任务，系统补问缺失信息并在提交前停下；③ 关闭模型接口后，快捷栏仍能完成相同任务。每次提交代码时运行类型检查和三个任务脚本；每月末由另一位成员按使用说明从零启动并录屏复现。

## 8. 试用、数据与失败应对

每位测试者用随机编号。统计表只记录编号、任务版本、是否完成、耗时、步骤数和 1—5 分清晰度评分。演示任务使用虚构信息；不要求测试者输入真实姓名、手机号、密码或业务账号。公开截图只截演示数据。若测试者自愿留下联系方式用于安排试用，联系方式单独保存，不与任务记录混在一张表。

评测工具不能单独判定网站符合 WCAG；自动扫描之外保留键盘和屏幕阅读器走查。若无法招募足够的老年或视障用户，报告分别列出普通测试者与目标用户的实际人数，不用前者代替后者。若外部网站无法接入，按自建演示站完成两个闭环并明确说明适用范围。若模型服务不可用，用户端快捷任务继续运行，开发端问题单与人工修复流程继续运行。
